## Purpose

Making an unmatched key visible as work to be done, on whichever side of the join it appears, so that a campaign delivering under a different name and a campaign delivering nothing at all stop looking the same.

## ADDED Requirements

### Requirement: Exceptions have a defined set of types

The system SHALL record exceptions of three types: `unmatched_delivery`, `missing_delivery` and `channel_mismatch`. The `channel_mismatch` type is defined but not yet generated, because neither the DSP statistics API nor the manual upload carries a line format.

#### Scenario: A channel mismatch is not generated by the current routes
- **WHEN** delivery is ingested through the DSP API or through a manual upload
- **THEN** no `channel_mismatch` exception is recorded

### Requirement: Unmatched delivery is recorded as an exception

The system SHALL record delivery that resolves to no campaign line as an `unmatched_delivery` exception carrying the DSP and the external identifier pair that failed to match, and SHALL NOT discard it. There SHALL be at most one such exception per DSP and external identifier pair, whatever its status, and it SHALL hold the first and last dates of its retained delivery.

#### Scenario: Delivery with no campaign line is kept
- **WHEN** an ingestion run retrieves delivery whose external key matches no campaign line and whose impressions or media cost is not zero
- **THEN** an exception is recorded naming that external key and the batch
- **AND** the delivery figures are retained per date, with impressions, clicks, media cost, measurable impressions and viewable impressions, rather than dropped

#### Scenario: The run completes despite unmatched rows
- **WHEN** an ingestion run encounters unmatched delivery
- **THEN** the matched delivery is still stored
- **AND** the run's outcome reports how many rows went unmatched

#### Scenario: Running the same window again does not duplicate the exception
- **WHEN** the same window is ingested twice and the same external pair is unmatched both times
- **THEN** one exception exists for that pair
- **AND** its retained delivery holds one row per date, the second run's figures replacing the first run's for the dates in the window

#### Scenario: Several unmatched rows for a pair and date are combined
- **WHEN** a run retrieves more than one unmatched row for the same pair and date
- **THEN** the retained delivery holds one row for that date with the figures summed

### Requirement: Unmatched rows with no impressions and no cost are ignored and counted

The system SHALL NOT record an exception for an unmatched row whose impressions and media cost are both zero, and SHALL count such rows on the batch as zero unmatched rows. The statistics API returns rows with no impressions for active campaigns, and treating them as exceptions would bury the real ones.

#### Scenario: An unmatched row of zeros is counted, not worked
- **WHEN** a run retrieves an unmatched row with zero impressions and zero media cost
- **THEN** no exception is recorded for it
- **AND** the batch counts it among its zero unmatched rows

#### Scenario: An unmatched row with impressions or cost is worked
- **WHEN** a run retrieves an unmatched row with impressions or media cost different from zero
- **THEN** an `unmatched_delivery` exception is recorded for its pair

### Requirement: A row without an attributed line item is not an exception

The system SHALL NOT turn a row that the DSP reports without an attributed line item into an exception of any type; such rows are ignored and counted on the batch.

#### Scenario: A row without a line item is counted on the batch only
- **WHEN** a run retrieves a row with no attributed line item
- **THEN** no exception is recorded for it
- **AND** the batch counts it among its ignored rows

### Requirement: A line with no delivery in a finished period is an exception

The system SHALL record an active campaign line as a `missing_delivery` exception when the sum of its impressions across a campaign period is zero, or when it has no delivery row in that period at all, evaluated once the last day of the period is on or before D-1. There SHALL be at most one such exception per line and period.

#### Scenario: A finished period with no rows is flagged
- **WHEN** a period has ended and one of its active lines has no delivery row in it
- **THEN** an exception is recorded against that line and period

#### Scenario: A finished period with only zero impressions is flagged
- **WHEN** a period has ended and every delivery row of one of its active lines has zero impressions
- **THEN** an exception is recorded against that line and period

#### Scenario: A period still running is not flagged for absence
- **WHEN** a period's last day is after D-1
- **THEN** no absence exception is raised for its lines

#### Scenario: Evaluating twice does not duplicate the exception
- **WHEN** the absence check runs again for a line and period that already has an exception
- **THEN** no second exception is created

### Requirement: Exceptions are worked, not just listed

The system SHALL let an operations user resolve an exception, SHALL keep an unresolved exception visible until it is, and SHALL record when it was resolved, by whom, and an optional note. Resolving an exception only marks it: it does not reprocess anything, and retained delivery is not moved into the delivery table.

#### Scenario: An exception can be resolved
- **WHEN** an operations user resolves an exception
- **THEN** it is marked resolved with the time, the user and the optional note
- **AND** it leaves the outstanding queue
- **AND** the record and its retained delivery remain readable

#### Scenario: Resolving does not reprocess
- **WHEN** an `unmatched_delivery` exception is resolved
- **THEN** its retained delivery is not added to the delivery table

#### Scenario: New delivery for a resolved pair is retained without reopening it
- **WHEN** a run retrieves new unmatched delivery for a pair whose exception is already resolved
- **THEN** the delivery is added to that exception's retained delivery
- **AND** the exception stays resolved

#### Scenario: Resolving an exception that is already resolved is a conflict
- **WHEN** an operations user resolves an exception that is already resolved
- **THEN** the request is rejected as a conflict

#### Scenario: Resolving an exception that does not exist
- **WHEN** an operations user resolves an exception that does not exist
- **THEN** the request is rejected as not found

#### Scenario: The queue can be read by status
- **WHEN** an operations user requests the exceptions with a status of open or resolved
- **THEN** only the exceptions with that status are returned

#### Scenario: Reading the queue requires the operations role
- **WHEN** a user without the `operations` role requests the exception queue
- **THEN** the request is rejected as forbidden

#### Scenario: Resolving requires the operations role
- **WHEN** a user without the `operations` role resolves an exception
- **THEN** the request is rejected as forbidden
